## 1. 무엇을 만들고 있나

**LLM을 이 NPU에서 돌리는 컴파일러**다.

```
입력   HuggingFace 모델 (또는 우리가 정의한 같은 구조)
출력   NPU 명령어 목록 하나 + 메모리에 처음 올려둘 데이터 한 덩어리
```

이 기계에는 운영체제도, 메모리 할당기도, 분기 명령도 없다. **프로그램 전체가
하나의 직선 명령 나열**이고 모든 주소가 컴파일 시점 상수다. 그래서 컴파일러가
정해야 할 것이 보통보다 훨씬 많다.

**핵심 제약**: 연산 유닛은 **8 MiB SRAM만** 읽는다. 전역 메모리(16 GiB)는
DMA로만 닿는다. 그런데 가중치 하나가 이미 SRAM보다 크다(`[3072,3072]`
fp16 = 18 MiB). 그래서 **모든 텐서를 조각내어 SRAM에 올렸다 내리기를 반복**해야
하고, 그 조각을 얼마나 크게 잡느냐가 성능을 정한다. 이것이 **메모리 플래닝**이고
최근 작업의 주제다.

## 3. C-model을 어떻게 확장했는가

`_poc/mysim_v09.cpp`는 벤더 재현이 **아니다.** 벤더 0818 모델을 출발점으로
삼되, LLM을 실제로 돌릴 수 있게 **필요한 최소만 더한** 우리 설계다.
원칙은 `ISA_V09.md`에 적힌 대로 **"ver.08 구조를 유지하고 최소만 추가한다"**이다.

### 더한 것

| # | 확장 | 왜 |
|---|---|---|
| **M1** | 전역 메모리를 **32-bit 칸 단위 32-bit 주소**로 (16 GiB) | 3B 모델의 가중치가 6 GiB다. 기존 주소 공간으로는 모델이 안 들어간다 |
| **M2** | **SRAM 8 MiB, nibble(4-bit) 단위 주소** | ver.08의 32-bit 주소 필드를 그대로 쓰면서 유효 24-bit로 8 MiB를 덮는다. 필드를 늘리지 않았다 |
| **M4** | 피연산자 서술자에 **dtype 2-bit** (`00=FP16 01=FP32 10=INT8 11=INT4`) | 양자화를 하려면 같은 명령이 int8을 먹어야 한다. **0x88/0x89의 남는 비트 [26:25]에 넣었다** — 그래서 **손대지 않은 ver.08 프로그램은 dtype FP16으로 그대로 돈다** |
| **M5** | **DMA 명령** `GLOAD 0xA0` / `GSTORE 0xA8` | 전역↔SRAM 이동 수단. dtype 무관, 동기, 4-word |
| **S1** | **dequant를 matmul 안에서** — K 타일 곱이 FP32 누적기에 들어갈 때 scale을 곱한다 | scale의 분배법칙 덕분에 **기존 MAC 비트가 그룹 양자화 사슬까지 담당**한다. 새 명령이 필요 없다 |
| — | **HALT(0xFF)가 전역 이미지를 파일로 남긴다**, `SNAPSHOT(0xF0)`은 중간 저장 | 결과를 읽어올 방법과, 어느 커널에서 틀어졌는지 추적할 방법 |
| — | **범위를 벗어난 접근은 즉시 에러** | 벤더 모델은 조용히 잘랐다. 그 조용함 때문에 잃은 시간이 많다(§8 참조) |

### 확장이 벤더 동작을 깨지 않는다는 확인

`tests/test_cmodel_v09_compute.py`가 **벤더 0818 재현본과 직접 대조**한다
(`test_fp16_vector_battery_matches_0818`, `test_fp16_matmul_battery_matches_0818`).
dtype 비트를 건드리지 않은 프로그램은 ver.08과 같은 결과를 내야 하고, 그것을
매번 확인한다. 확장을 더할 때 이 대조를 깨지 않는 것이 조건이다.

### 산술 계약

**FP16 저장 / FP32 계산 / 저장할 때 RNE 반올림.** 행렬 유닛의 누적기는 FP32
하나뿐이다. 이 "내부 FP32 누적"이 정확도 판정 기준의 근거다 — **우리 기계가
llvm 빌드보다 정확하다**(llvm은 fp16으로 누적한다).

### ver.08의 결함 중 고친 것

- reduce-max에 **시드**를 준다 (모든 값이 음수여도 정확)
- 16-bit 즉값을 **부호 있는 정수**로 읽는다
- 활성화 코드 1을 **표준 tanh-GELU**로

### 실행 방법

컴파일러가 알아서 빌드한다 — `npu_compiler/v09_runtime.py`가 소스보다 오래된
바이너리를 발견하면 `g++ -O2`로 다시 만든다. 산출물은
`d_compiler/build/mysim_v09`.

실행은 디렉터리 하나에 파일 두 개를 놓고 부르는 방식이다:

```
입력  global_memory.bin      전역 메모리 초기 이미지
      program_memory.bin     명령어 나열
출력  saved_global_memory.bin  HALT 시점의 전역 이미지
      perf_counters.txt        DMA 셀 수, 명령 수 등
```

> **주의**: 전체 모델 실행은 이미지를 **두 벌**(입력 + 저장) 쓴다. FP16 28층이면
> 약 12 GiB, 양자화면 약 6 GiB다. 디스크가 모자라면 쓰기가 잘리는데, 그때
> 나오는 메시지가 무엇을 말하는지는 §8에 있다.

## 4. 컴파일러 구조 (요약)

자세한 것은 `report_0901.md`. 여기서는 어디를 만져야 하는지만.

```
모델
 ├─ 1. 프론트엔드      Relax 그래프로            npu_compiler/nn_models/
 ├─ 2. 그래프 pass     전부 TVM 표준             npu_compiler/tvm_pipeline.py
 ├─ 3. 루프로 낮추기   LegalizeOps               npu_compiler/legalize.py, npu_legalize.py
 ├─ 4. 주소 정하기     StaticPlanBlockMemory     npu_compiler/npu_memplan.py
 ├─ 5. 스케줄  ★       타일링 + SRAM 복사        npu_compiler/npu_intrin.py
 ├─ 6. codegen         TIR을 걸어가며 명령 방출   npu_codegen/*.cc (C++), tir_codegen_v09.py (정의·폴백)
 └─ 7. 링크            직선 명령 하나로 + peephole  npu_compiler/npu_link.py
```

**설계 원칙 두 가지** (이걸 지키는 것이 중요하다):

1. **표준 TVM 경로를 기본으로 한다.** 모델 정의부터 주소 배정까지 TVM이 주는
   단계를 그대로 쓰고, 우리 것은 표준이 마련해 둔 **확장 지점**(커스텀 legalize
   map, 커스텀 pass, tensorize 인트린식)에만 끼워 넣는다. 손으로 짠 옛
   컴파일러(`backend_v09.py`)는 **정답 대조용으로만** 남긴다.
2. **기계가 특이하다는 사실을 마지막 단계에만 가둔다.** 직선 프로그램, 할당기
   없음 같은 특성은 6~7단계에서만 나타나고 그 앞은 보통의 TVM이다.

> **이 원칙을 어긴 곳이 한 군데 있다** — W8A8 곱셈. §7에 적었다.

### 프론트엔드 네 가지

| 이름 | 무엇 |
|---|---|
| `nn_models/llama.py` · `qwen3.py` · `gemma.py` | 구조를 `relax.frontend.nn`으로 우리가 정의하고 체크포인트를 이름으로 싣는다 |
| **`nn_models/hf.py`** | **HF 모델 자체가 입력.** `torch.export`가 HF의 `forward`를 추적하고 TVM 표준 torch 프론트엔드가 Relax로 옮긴다 |

## 7. 남은 작업

### 성능

| | 항목 | 크기 | 비고 |
|---|---|---|---|
| 1 | HF 경로의 `reshape`·`cast` 정리 | seq 512에서 **316 MB** (reshape 174 + cast 142) | 값을 바꾸지 않는 연산이라 없애도 정확성에 영향 없음. 표준 pass로 가능 |
| 2 | lm_head 마지막 행만 계산 | 28층 seq 512에서 프로그램 **−5.8%**, 이동량 −0.9% | seq ≤ 64에서는 이득 0. 정확성 검사가 전체 logits을 쓰므로 그쪽을 먼저 정리 |

### 구조 (성능이 아니라 유지보수)

| | 항목 | 성공 기준 |
|---|---|---|
| 3 | **스케줄 템플릿 4개를 하나로** | **아무것도 안 바뀌어야 정상.** 게이트 word가 완전히 동일해야 한다 |
| 4 | **W8A8을 표준 경로로 완전히 이전** | §7의 예외를 없애는 것 |

**3번이 왜 필요한가**: 지금 스케줄 함수가 넷이다(`schedule_matmul_sram`,
`schedule_generic_sram`, `schedule_generic_striped`,
`schedule_attention_blocked`). 실제로 겪은 비용이 있다 — 어텐션에 넣은 개선
규칙 하나가 다른 템플릿엔 없어서, 같은 낭비가 다른 커널에 남아 있었다.
`report_0908.md` §4.5에 자세히.

**4번의 현재 상태**: `npu_link.py`에 예외가 하나 있다.

```python
if npu_w8a8.is_w8a8(prim):
    npu_w8a8.emit(...)      # 손으로 쓴 명령 시퀀스
    continue                # ← 스케줄 경로를 안 거친다
```

**이것이 §4의 원칙을 어기는 유일한 곳이다.** 절반은 옮겼다 — int8 곱셈용
tensorize 표식(`npu_gemm_acc_sram_int8`)이 있고 스케줄이 dtype으로 그걸 고른다.
막힌 것은 나머지 절반이다:

> **VQUANT 한 명령이 나눗셈·반올림·포화를 다 한다.** 양자화 pass는 그것을
> `round(min(max(x/scale)))`로 *서술*하는데, 그대로 명령으로 옮기려면
> `round`(half-to-even)가 필요하고 **기계에 그 명령이 없다.** 즉 느린 게 아니라
> 표현이 안 된다. 표준 경로로 가려면 그 사슬을 **다시 VQUANT로 패턴 매칭**해야
> 한다.

그래서 지금은 손 시퀀스를 유지하되 **거기에 메모리 플래닝을 넣어** 두었다
(가중치 열 단위 상주 + 행 패널). 그 결과 W8A8이 모든 길이에서 FP16보다 낫다.
자세한 것은 `report_0908.md` §6.7.

### 재어 보고 보류한 것 (다시 하지 말 것)

| 항목 | 측정 결과 | 어디 |
|---|---|---|
| 커널 **사이**에 SRAM 유지 | 순이득 seq 512에서 **+2.9%**, seq 2048에서 **음수** | §6.1 |
| 커널 **안**의 SRAM 절약 (생존구간 재사용 / 원소별 블록 인라인) | **둘 다 트래픽 불변** | §6.4 |
| W8A16 양자화 | 통과하지만 **프로그램이 54배** | §6.6 |

**셋 다 "해 보면 좋을 것 같다"에서 출발해 재 보니 0이거나 손해였다.**
다시 손대기 전에 그 절을 읽는다. 재개할 조건도 적어 두었다.

### 하드웨어·ISA 대기

- **비동기 DMA / double buffering** — ISA에 barrier가 없어 전송·연산을 겹칠 수
  없다. 여기서부터는 바이트가 아니라 겹침이 관건이라 벤더의 숫자(대역폭·지연)가
  필요하다
- **더 큰 SRAM** — 남은 초과분 30%의 유일한 근본 해결책

## 8. 알려진 함정 — 이것 때문에 시간을 잃었다

### (1) 게이트가 전부 seq 7이다

전체 깊이 게이트 네 개가 **7토큰 프롬프트**로 돈다. 그런데 seq 7은 하필
**여러 결함이 드러나지 않는 지점**이다.

| 결함 | seq 7에서 안 보인 이유 |
|---|---|
| 긴 프롬프트가 컴파일 안 됨 | 텐서가 작아서 SRAM에 다 들어갔다 |
| 가중치를 M÷64회 다시 읽음 | M=7이면 덩어리가 하나뿐이라 어차피 한 번이다 |
| W8A8이 FP16보다 느림 | seq 7이 W8A8이 **유일하게 이기는** 지점이었다 |
| lm_head 낭비 | 64행 미만은 어차피 최소 단위다 |

**새 기능을 넣으면 긴 프롬프트에서 따로 재라.** `analyze_traffic.py`가 그걸
위해 있다.

### (2) decode 게이트가 capacity를 프롬프트에서 계산했다

`run_nn_generate.py`의 기본 capacity가 `프롬프트 + 토큰 − 1`이다. 3토큰
생성이면 **capacity 9**로 돌았다. 실제 문맥 길이(512)에서는 **링크가 아예
실패**하고 있었는데 아무도 몰랐다.

**decode를 볼 때는 `--capacity`를 현실적인 값으로 준다.**

### (3) 조용히 잘리는 필드, 조용히 되돌아가는 스케줄

- 인코더가 16-bit 필드에 큰 값을 넣으면 **마스킹**했다 → lm_head의
  `128,256 & 0xFFFF = 62,720`. 지금은 **예외를 던진다.** 새 필드를 만들 때도
  그렇게 한다
- 스케줄 변환이 실패하면 `try/except`가 삼키고 최소 설정으로 되돌아갔다.
  **어느 커널이 되돌아갔는지 로그에 안 남아** 트래픽의 30%를 일주일 동안
  낭비했다. 지금은 실패 시 어느 값에서 왜 실패했는지 말한다

### (4) 총량만 보면 못 잡는 버그가 있다

위 (3)의 30% 낭비는 **총 트래픽만 보면 "개선됨"으로 보였다.** 커널 단위로
쪼개서야 잡혔다. `analyze_sram.py`가 커널별로 이론상 최소와 비교해 준다.

### (5) llvm 빌드는 우리보다 **덜** 정확하다

정확성 대조에 llvm 빌드를 쓰면 안 된다 — llvm은 **fp16으로 누적**해서 K가
크면(3072~8192) 스스로 드리프트한다(cosine 0.998). 우리 기계는 FP32로 누적한다.

**대조 기준의 서열**: `float32 numpy` > `우리 기계` > `llvm 빌드`.
`test_long_prompt.py`가 float32와 대조하는 이유다. 한 번은 이것 때문에
decode가 틀렸다고 오판했다.

### (6) 기록된 정답이 다른 모델의 것일 수 있다

decode 게이트가 오래 "실패"로 있었는데, **기대값이 Qwen3의 답**이었다.
지금은 리터럴 대신 **기록된 참조 npz에서 읽는다.**

### (7) 디스크

`/data2`는 **공유 볼륨**이다. 하루 안에 34 GB → 4.6 GB → 124 GB로 움직였다.
전체 모델 실행은 이미지를 두 벌 쓴다(FP16 28층 12 GiB, 양자화 6 GiB).

모자라면 C-model의 쓰기가 잘리는데, 예전에는 그 증상이
`malformed snapshot file size 766185472`로 나와서 컴파일러를 의심하게 만들었다.
**지금은 남은 공간과 필요한 크기를 함께 말한다.** 그래도 실행 전에
`df -h /data2 /`를 보는 편이 낫다.

## 9. 작업 방식에 대한 조언

이 프로젝트에서 반복해서 확인된 것이 하나 있다.

> **구조에서 추론한 예상이 자주 틀렸고, 재 보고 나서야 답이 나왔다.**

실제로 있었던 일:

| 예상 | 실측 |
|---|---|
| 커널 사이에 데이터를 유지하면 왕복 51%를 회수 | **+2.9%, 긴 프롬프트에서는 손해** |
| 커널 안 공간을 아끼면 블록이 커진다 | **0** |
| 브로드캐스트 규칙 누락이 비용이다 | 그건 아니었고 **다른 것**이 −3.3% |
| 양자화가 남은 30%의 열쇠다 | 구현이 **오히려 느렸다** |
| lm_head가 ×seq 낭비다 | 28층에서 **−5.8%** |

그래서 **고치기 전에 재는 것**을 기본으로 한다. 분석 도구 네 개가 전부
실행 없이 링크만으로 답을 주므로 몇 분이면 된다.

그리고 **변경마다 무엇이 안 바뀌어야 하는지를 먼저 정한다.** 예를 들어
어텐션 블로킹은 "seq 7 게이트의 word가 한 개도 달라지면 안 된다"였고, 실제로
15,285,445로 동일한 것을 확인하고 나서야 진행했다.
